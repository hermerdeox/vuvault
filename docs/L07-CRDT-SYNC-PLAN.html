L07 · Tier 2 · 2027 Q2

Encrypted CRDT sync — what it takes to ship.

Plan-of-record for L07 from the VuVault roadmap. Item-level CRDTs over the existing M3 D1/R2 sync transport, field-wise encrypted with HPKE (RFC 9180) under a per-vault hybrid X25519 + ML-KEM-768 key. Server sees opaque ciphertext deltas; cannot infer item structure, fields, or relations.

L07 turns a vault from a single AES-GCM blob into a stream of field-level deltas encrypted with HPKE under a per-vault hybrid X25519 + ML-KEM-768 key. Two devices sharing a vault each hold the same hybrid private key (distributed via L06 MLS or L08 WebRTC pairing) and apply each other's deltas locally via Yjs CRDT merge semantics. The server sees an append-only log of opaque ciphertext frames, indexed by `(accountId, deviceId, sequenceClock)` — it cannot tell whether a delta is a password change, a TOTP rotation, or a new item; cannot tell two deltas modify the same item; cannot tell how many items exist (within bucketed padding); cannot replay across devices because each device has a distinct HPKE key-share.

The crucial architectural insight: L07 does not require a new transport. The M3 R2 blob endpoints already accept opaque ciphertext fragments authenticated by an OPAQUE KE3 bearer token. The change is (a) the blob is now a CRDT delta-frame instead of a sealed AES-GCM whole-vault envelope, (b) the server keeps an append-only log per account rather than one row, (c) the client maintains a Yjs in-memory document synced incrementally.

Foundations the plan builds on

L07 sits on top of every piece M3 already shipped. Nothing here re-invents the OPAQUE handshake or the bundle integrity verifier.

CRDT data model

Yjs is the chosen CRDT runtime. It is the only mature browser CRDT with a stable wire format (`Y.encodeStateAsUpdate`, `Y.applyUpdate`), a minimal footprint (~80 KB minified), and zero dependencies on a particular network transport. Each vault is one `Y.Doc`.

Document layout

vault: Y.Doc
├─ items: Y.Map<ItemId, Y.Map<FieldName, EncryptedField>>
├─ deletions: Y.Map<ItemId, Y.Map<'at' | 'by', Y.Text | number>>
├─ meta: Y.Map<'formatVersion' | 'createdAt' | 'lastEditAt', any>
└─ devices: Y.Map<DeviceId, Y.Map<'pairedAt' | 'lastSeen' | 'label', any>>

Each item is a nested Y.Map so that two devices editing different fields of the same item produce non-conflicting deltas. Per-field EncryptedField values are HPKE ciphertexts — the CRDT layer treats them as opaque Uint8Arrays. The cleartext is derived in a shadow map kept only in `vault-session.ts`'s memory footprint; it never enters the Yjs document state.

Why field-level rather than item-level

  • A password rotation generates one delta of ~120 bytes (HPKE-encrypted new password). Item-level encryption would require re-encrypting every field whether changed or not.
  • Conflict resolution is mechanical: password is last-writer-wins per device clock; tags are a Y.Array (commutative add/remove); notes is a Y.Text with character-level merge. Yjs does all of this by construction — VuVault writes zero merge code.
  • Server cannot tell which field changed because the ciphertext envelope hides the field name (the HPKE AAD binds the field name but the ciphertext is field-name-agnostic from outside).

Cryptographic envelope (HPKE + hybrid KEM)

Each field write generates one HPKE single-shot encryption (RFC 9180), Mode-Base, with the following suite:

HPKE componentChoiceRationale
KEMDHKEM(X25519, HKDF-SHA-256) + ML-KEM-768 concatHybrid PQ-safe like M2's envelope. Use concatKDF(X25519_ss, ML_KEM_ss) as the KEM shared-secret. ML-KEM-768 (smaller than 1024) because per-field deltas value bandwidth more than headroom.
KDFHKDF-SHA-512Same KDF as M2; no new primitives to audit.
AEADAES-256-GCMSame AEAD as M2; reuse @noble/ciphers/aes.

Per-vault key derivation

// At provisioning time (one-time)
exportKey      = OPAQUE.exportKey                  // from M3 KE3
vaultSyncSeed  = HKDF(exportKey, "vuvault-l07-sync-seed-v1", deviceSalt, 64)
hybridSeed     = HKDF(vaultSyncSeed, "vuvault-l07-hybrid-v1", null, 32)
(xPub, xPriv)  = x25519.fromSeed(hybridSeed[0..32])
(kPub, kPriv)  = ml_kem768.keygen(hybridSeed[32..64])
vaultPubBundle = xPub || kPub                      // 32 + 1184 = 1216 bytes
vaultPrivBndl  = xPriv || kPriv                    // 32 + 2400 = 2432 bytes

Encrypt-one-field

seal(field: { itemId, name, value }, deviceId, lamportClock):
  ad   = "vuvault-l07-ad-v1" ||
         formatVersionByte    ||  // 0x03
         accountIdBytes       ||  // server-allocated; bound for replay-resist
         deviceIdBytes        ||  // 16 bytes; per-device clock binding
         u64be(lamportClock)
  // RFC 9180 §6.1 single-shot:
  (enc, ct) = HPKE.SealBase(vaultPubBundle, info="l07-field", ad, plaintext = encode(field))
  frame     = enc || ct
  return frame                    // ~ 1216 + len(field) + 16 (AEAD tag) bytes
Why include the field name in the plaintext, not in the AAD. Putting the field name in the AAD would force a different ciphertext per field even for identical values, which is fine, but it would also let an attacker who learns one plaintext run a field-name oracle against future ciphertexts. Encoding the field name inside the plaintext keeps the ciphertext semantics-blind to a server inspector.

Decrypt

open(frame: Uint8Array, deviceId, lamportClock):
  enc, ct = split(frame, hpke.encSize)            // 1216 bytes prefix
  field    = HPKE.OpenBase(vaultPrivBundle, enc, info="l07-field", ad, ct)
  return decode(field)

API surface

EndpointMethodAuthBehavior
/api/sync/deltas POST Bearer KE3 token Body: { sequenceClock, frame: base64 }. Strict monotonicity per session; cross-session monotonicity comes from MAX(sequence_clock) at KE3 mint. R2 put + D1 row + sequence_clock advance, atomic per the existing advanceSequenceClock pattern.
/api/sync/deltas?since=N&limit=K GET Bearer KE3 token List up to K frames with sequence_clock > N. Frames are concatenated R2 reads, capped at 4 MiB per page.
/api/sync/snapshot POST Bearer KE3 token Operator-initiated checkpoint: client uploads Y.encodeStateAsUpdate(doc) then a delta tombstone marks all prior deltas as superseded. Server prunes superseded deltas during nightly cron. Same wire shape as /api/sync/deltas.
/api/sync/capabilities GET Public Adds { crdtSync: true, maxFrameBytes, maxDeltasPerSession }. Existing /api/capabilities route extended.
The existing /api/blobs/upload and /api/blobs/latest routes stay. A v2 vault and a v3 vault can coexist on one account during migration; the capabilities endpoint tells the client which protocol the server prefers.

Client-side architecture

Three new TypeScript modules; one existing module changes substantially.

New modules

ModuleResponsibility
src/lib/crypto/hpke.ts RFC 9180 single-shot Mode-Base on the X25519+ML-KEM-768 hybrid suite. Hand-rolled on top of @noble/curves/ed25519 + @noble/post-quantum/ml-kem. KAT-locked against a custom vector set (RFC 9180 has no L07-relevant KATs; we ship our own + cross-check the X25519 leg against RFC 9180 §A.1).
src/lib/services/crdt-doc.ts Wraps Y.Doc with the field-level encrypt/decrypt boundary. Exposes a VaultDoc object whose public API mirrors the M1 vault store but emits Yjs updates instead of full re-encrypts.
src/lib/services/delta-sync.ts Pull/push loop. Calls /api/sync/deltas on a debounced cadence (5 s after a local write; on focus; on visibilitychange). Persists the latest server sequence_clock in Dexie so the next session can resume.

Migration: v2 single-blob → v3 CRDT-deltas

Same shape as the v1→v2 transparent upgrade. On first save after a v2 unlock, the client:

  1. Reads the decrypted item list (in-memory after openVault).
  2. Constructs a fresh Y.Doc and applies every item as one initial delta.
  3. Encodes the full state as a snapshot (Y.encodeStateAsUpdate), seals each field with HPKE, and POSTs the bootstrap delta to /api/sync/deltas with sequenceClock = 1.
  4. Atomically updates the Dexie account row to formatVersion = 3 and writes the encoded Yjs state into vault-state.
  5. Calls /api/blobs/upload one last time with a tombstone sentinel so the server-side cron can prune the v2 blob.
Downgrade is impossible. The migration is one-way; v3 vaults cannot revert to v2 without losing the delta history. This is acceptable because v3 is strictly more capable. The upgrade ships with a "you can revert before your next save" 24-hour grace window enforced by a tombstone TTL on the server.

Cross-device key distribution

Two devices need the same vaultPrivBundle to decrypt each other's deltas. There are three viable paths; the plan picks one and tracks the others as alternatives.

PathTrust modelDependencyVerdict
(A) Re-derive on every device OPAQUE export key + same device salt None beyond M3 Plan-of-record. The OPAQUE export key is reproducible per device given the user's Secret Key and an OPAQUE login. Use a per-vault salt persisted by the server (or derived deterministically from accountId). Every paired device that completes OPAQUE login derives the same vaultPrivBundle.
(B) L08 WebRTC pairing Local-network ECDH + QR-code mutual auth L08 (also Tier 2) Plan-of-alternative when devices cannot complete OPAQUE login (e.g. ephemeral browser).
(C) L06 MLS group Group-ratcheted L06 Required for multi-user sharing (family/team). L07 single-user just needs (A); L07 + L06 for multi-user.

Path (A) — re-derive flow

// Per-vault salt is server-side, but PUBLIC (it's not key material).
// Server returns it during /api/opaque/login/ke3 alongside the bearer token.
saltPerVault = HKDF(serverIdentity, "vuvault-l07-vault-salt-v1", accountId, 16)

// Each device, after OPAQUE login:
exportKey      = client.loginFinish(...).exportKey
vaultSyncSeed  = HKDF(exportKey, "vuvault-l07-sync-seed-v1", saltPerVault, 64)
hybridSeed     = HKDF(vaultSyncSeed, "vuvault-l07-hybrid-v1", null, 32)
(xPriv, kPriv) = (deterministic from hybridSeed)

This means a stolen device plus the Secret Key reproduces the vault key — same threat model as M2. It is not a server-trust downgrade; the server never sees the export key.

Zero-knowledge boundary & metadata leakage analysis

The marketing claim must stay honest. Below is exactly what the L07 server can and cannot infer.

Server learnsServer cannot learn
Whether the account exists (account-existence oracle, same as today). Vault size in items (deltas don't add a row per item).
Total bytes uploaded per account, per hour. Which item changed (no per-item identifier on the wire).
Number of deltas (frame count). Which field changed (field name lives inside the ciphertext).
Time-of-edit (delta created_at). Plaintext of any field (HPKE-sealed).
Device ID per delta (so it can enforce per-device sequence clocks). Whether two deltas target the same item (each frame is independent ciphertext).
Bucketed size class (64 / 256 / 1024 / 4096 / 16384 B). True field length within a bucket.
Known oracle: The server can correlate device IDs to editing cadence (e.g. "device X always writes between 9am and 5pm"). The mitigation is to randomize delta-flush timing within a ±30 s jitter window and to bound the per-account leak via Cloudflare WAF on cross-IP-pattern analytics. We document this in SECURITY.md ZK-scope.

Implementation phases & deliverables

Phase A — Crypto primitives & KATs (2 weeks)

  • Implement src/lib/crypto/hpke.ts with the X25519+ML-KEM-768 hybrid suite.
  • Lock byte-stable KATs in src/lib/crypto/kat/hpke-l07.json. 8–12 vectors covering empty-AD, fixed-AD, multi-byte field names, all five bucket sizes.
  • Add src/lib/crypto/hpke.kat.test.ts so npm run test:fips includes the L07 KAT runner alongside the FIPS 203 + RFC 9106 suites.
  • Append @noble/curves / @noble/post-quantum already pinned; add nothing new at the dep layer here.

Phase B — Yjs integration & VaultDoc wrapper (2 weeks)

  • Add yjs as a runtime dep (already noted as "future CRDT" in CURSOR_PROMPT.md).
  • Implement src/lib/services/crdt-doc.ts. Mirrors the M1 vault store surface (add/update/remove/items) but emits Yjs updates.
  • Vitest unit suite: deterministic round-trip, two-device merge, conflict-resolution per field kind, tombstone semantics.
  • Property tests: 1000 random op sequences, verify final state is identical regardless of merge order.

Phase C — Wire protocol & D1/R2 routes (1.5 weeks)

  • Migration migrations/0002_l07_deltas.sql.
  • New SvelteKit routes under src/routes/api/sync/: deltas/+server.ts (POST + GET), snapshot/+server.ts. Same fail-closed rate-limit gating as M3.
  • Extend /api/capabilities with the v3 negotiation.
  • Integration tests: append-only-monotonicity, per-device clock isolation, 4 MiB page cap, R2 + D1 atomicity.

Phase D — Client sync loop (1.5 weeks)

  • Implement src/lib/services/delta-sync.ts with the debounce + visibility-change + focus cadence.
  • Wire into vault.svelte.ts: the existing syncNow() action calls the new module when formatVersion === 3, the old module when formatVersion <= 2.
  • Add Dexie deltas + vault-state tables and an upgrade hook.
  • Per-tab CRDT awareness: existing tab-sync BroadcastChannel forwards Yjs updates between tabs without going through the server.

Phase E — v2 → v3 migration on save (1 week)

  • One-way upgrade inside vault-session.ts::saveItems.
  • Server-side cron worker (or scheduled trigger) that prunes v2 blobs after the 24 h tombstone TTL.
  • End-to-end test: provision v2 → unlock → save → confirm v3 + tombstoned v2.

Phase F — Multi-device E2E (1 week)

  • Extend tests/e2e/sync.spec.ts with a two-context Playwright run: device A adds an item, device B unlocks (deriving the same hybrid bundle from its own OPAQUE login), device B pulls A's delta, asserts the item materializes.
  • Concurrent-edit test: A and B both rotate the same password within 1 s; assert deterministic Lamport-clock resolution.

Phase G — Performance baseline & release gates (0.5 week)

  • Update PERFORMANCE-BASELINE.md with steady-state delta bandwidth, cold-start replay time, Y.Doc memory footprint, and the new vendor-yjs chunk size.
  • Add M4_L07_E2E_PASSED as a same-SHA CI artifact gate, identical to the M3 m3-sync-e2e pattern. The release workflow refuses production deploy without it.
  • Document the new burst-probe smoke (POST 12 deltas / GET 12 times) against the live deploy.

Phase H — Audit prep & ROADMAP refresh (0.5 week)

  • Prepare an L07 audit packet for the Tier 1 audit firm (Cure53 / NCC / Trail of Bits): the HPKE wrapper, the migration semantics, the metadata-leakage analysis, the KAT vectors.
  • Update ROADMAP.md from "⏳ Tier 2 / 2027 Q2" to "✅ Tier 2 / 2027 Q2" with concrete file citations, mirroring the M3 refresh pattern.

Out of scope
