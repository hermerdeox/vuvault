## TL;DR

Phase 2 ships the **V1-C2 closure** (no persistent device set) and the
L08 Option (ii) groundwork (per-request rotating bearer tokens, via
`Next-Token` response header). The V1-C2 release probe flips from
`expected_fail` → `pass` against a live local dev server. V1-C1 and
V1-C3 correctly remain `expected_fail` (their closure is Phase 4,
§L07b).

The level-flip (`CURRENT_LEVEL` 2 → 1) is intentionally **NOT** part
of this phase. Phase 6 owns the flip and gates it on a green
`.vu1-probe-passed` artifact carrying `v1_c1=pass v1_c2=pass
v1_c3=pass`. Today's artifact reads `v1_c1=expected_fail
v1_c2=pass v1_c3=expected_fail`, so the gate is correctly blocked.

### Static-guard rule (`scripts/audit-bindings.mjs`)

- New **Rule 4** (metadata-minimization). Dormant until
  `0004_metadata_minimization.sql` is in the apply chain (so old
  branches keep passing); active in this branch. Rejects any future
  migration that re-introduces a device-correlating column on
  `sessions` or `accounts` (`device_*`, `last_login_*`, `paired_*`,
  `fingerprint*`, `ip_*`, `user_agent`).

## Deliberate deferrals

### WebRTC + ECDH device pairing (`p2_webrtc_pairing`)

The plan bundled `src/lib/services/device-pairing.ts` (WebRTC + ECDH
P2P pairing transcript with QR-bound mutual auth) under Phase 2
because the brief's table named the phase "L08 + session-mint
redesign." We are deferring this module to a follow-up because:

- The V1-C2 closure is delivered ENTIRELY by the session-mint
  redesign half of §L08 (see the §L08 sub-section in
  `docs/TIER2-ARCHITECTURE.md`). The pairing transcript is a
  separate Tier-2 capability that does not gate the V1-C2 probe.
- Per the brief's §0.3 ("test everything you write") and §0.8 ("one
  phase, one PR"), shipping ~200+ lines of new WebRTC/ECDH code
  without an integration harness (Playwright cross-origin pair, or
  a deterministic mock signaling channel) is anti-pattern. The
  harness scaffolding is itself a meaningful PR.
- The deferral does **not** change Vu1 closure: the probe gate is
  the same whether or not the pairing module exists.

The pairing module will land as its own PR with its own tests and
its own verification report. The §L08 sub-section in
`docs/TIER2-ARCHITECTURE.md` already specifies the transcript and
unit-of-trust; that spec is the authority for the follow-up PR.

### Per-request rotation on `/api/v2/blobs/*`

`rotateToken()` is exercised today only by `/api/v2/sessions/self`.
The brief envisions Phase 4 / L08 Option (ii) extending rotation to
every authenticated route. We are NOT extending it in Phase 2
because:

- `/api/blobs/*` (v1) and `/api/documents/[blobId]` (v1) keep their
  durable bearer-token semantics; rotating them today would force a
  client-flow change with no V1-C2 closure benefit.
- The brief's "Phase 4 — §L07b" already plans for v2 blob routes
  with rotation built in from the start. Bolting rotation onto v1
  would be wasted refactoring.

## Risk + rollback

The 0004 migration is **destructive to columns**, not to data. The
columns dropped (`sessions.device_id`, `accounts.last_login_at`,
table `device_pairings`) carried zero semantic load: nothing in the
app's primary user flow reads them, and the only writers (`KE3`,
`/api/blobs/upload`, `/api/documents/[blobId]`) all live in this PR
and are simultaneously updated to stop writing.

If a rollback is needed before broader deploy:

1. Revert this PR.
2. Run the down-migration block at the bottom of
   `migrations/0004_metadata_minimization.sql` against the local D1
   (the down block is commented; uncomment + execute).
3. Re-run vitest — the prior expectations (with `device_id` etc.)
   were preserved in the same commit; reverting the commit restores
   them.

For a remote/production rollback the same steps apply, with the
caveat that any session row already created post-0004 will lack
`device_id`. The migration sentinel will reject the down operation
by default, so the operator must temporarily drop the
`metadata_minimization_guard` trigger before running the down SQL.
