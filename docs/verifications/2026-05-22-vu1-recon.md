## 3. Reference document summaries

### 3.1 `docs/TIER2-ARCHITECTURE.md` §L06–L10

- **§L06 (MLS sharing)** — Public interface sketch + `mls_groups`/`mls_membership` D1 tables. Library choice OPEN: `mls-rs`, `OpenMLS`, or `@web5/mls` — none pinned. Appendix B.4 sign-off needed.
- **§L07 (CRDT sync — what the brief calls L07a)** — Yjs-based per-update encrypted delta stream. Defines `vaults/{accountId}/crdt/{updateIndex}.bin` R2 layout. **Padding profile open** (power-of-two vs k-anonymity). **Does NOT close V1-C1** — the per-account prefix is preserved.
- **§L08 (WebRTC pairing)** — Server-free pairing transcript. Threat-delta table at the bottom explicitly says: *"Server learns device-set: **Same**; pairing itself is peer-to-peer but session minting still hits server."* Same admission as VU-LEVEL-MIGRATION-MAP §V1-C2.
- **§L09 (AKD)** — CONIKS-derived Merkle log anchored to Sigstore Rekor. VRF family OPEN (P256-VRF vs Ed25519-VRF vs Parakeet alternative). **Does not specify per-request unlinkable handles** (that's the L09cap gap the migration map calls out).
- **§L10 (PIR breach checks)** — Orthogonal to the level ladder; doesn't gate Vu1.

A `> Vu Level migration` callout was added by the prior audit pass to the top of `TIER2-ARCHITECTURE.md` listing the three required sub-specs (L07b, L08 session-mint redesign, L09cap) — Phase 1 of this plan is exactly producing those three.

### 3.2 `docs/PRIVACY-LEVEL.md` — inverted ladder

- Lower number = stronger privacy (post-2026-05-20 inversion).
- Vu Level 0 = zero-knowledge, Vu Level 5 = banned floor.
- **Vu Level 2 = today's shipped state.** Documented in the TL;DR as "vault + documents end-to-end encrypted, M3 sync gated and verified; server retains account / session / device metadata."
- **SubZero** (honorary tier above Vu Level 0) is referenced in the reference table as the externally-anchored provable-ZK target — requires SubZero CSP, public audit, and formal-verification-grade evidence per `PRIVACY_AUDIT.md` §15.
- The "What is partial or pending" table lists field-level CRDT sync, blob size/timing padding, multi-device pairing without server device-set, sharing, cross-device document recovery, FROST recovery, PIR breach checks, and zkSNARK selective disclosure as ⚠ pending/partial.

### 3.3 `PRIVACY_AUDIT.md` §8, §15, F-003

- **§8 — Metadata & Side Channels:** the server can observe (a) account existence (KE1 401 oracle), (b) stable `accounts.client_id`, `sessions.device_id`, `sessions.sequence_clock`, `accounts.sequence_clock`, `last_login_at`, (c) R2 object keys revealing per-account blob counts, update sequence, document UUIDs, sizes, and upload times. Cloudflare itself sees IP/UA/path/timing/TLS metadata. All of this caps the project at canonical Vu2.
- **§15 — Legacy Taxonomy Translation:** maps the old in-app ladder to the canonical scale (SubZero / Vu0 / Vu1 / Vu2 / Vu3 / Vu4 / Vu5). Verdict: current implementation = canonical Vu2.
- **F-003 [HIGH] Persistent account/session metadata caps the project at canonical Vu2:** location `migrations/0001_init.sql:37`. Recommendation: *"Either lower claims to canonical Vu2, or redesign sync around unlinkable identifiers, blinded routing, and metadata minimization with explicit limits."* This is the audit's anchor for Phase 4 L07b + Phase 2 L08-redesign.

### 3.4 `docs/SECURITY.md` §3 / §scope

- **§"Scope of the zero-knowledge claim"** explicitly enumerates 6 claims. Claims (3) "size from blob" and (4) "page count" are flagged as "planned in Tier 2 — current implementation does not pad." Claim (5) "device set" is flagged as "planned in Tier 2 — depends on the L08 device-pairing flow; today every successful OPAQUE login mints a server-side session token."
- The doc explicitly lists out-of-scope: (a) account-existence oracle, (b) total sync volume, (c) IP correlation. These align with the V0-C3 (account oracle) and V0-C1 (routing identifiers) criteria in the migration map.

### 3.5 `scripts/release-probe-opaque.mjs` — existing probe pattern

- Pure `.mjs`, no TS imports. Depends only on `@structured-id/opaque` (already in `package.json`).
- Uses OPRF primitives directly (`oprfBlind`, `serializeKE1`, `clientAkeStart`) rather than the high-level `OpaqueClient` class, because the library's WASM backend throws for protocol methods on Node.
- Reads `PUBLIC_SYNC_ORIGIN` and `RELEASE_SHA` from env.
- Emits `console.log` + sets process exit code 1 on any fail. **Does NOT emit a machine-readable artifact today** — that pattern is reserved for the `m3-sync-e2e` job below.
- Runs two probes against the live origin: (1) real OPAQUE registration request shape, (2) login KE1 against unknown clientId returns 401 (not 5xx).

The Phase 1 §4.5 V1 probe harness should preserve this style — pure `.mjs`, no new dependencies, OPRF primitives only.

### 3.6 `m3-sync-e2e` gating pattern

The template Phase 6 Vu1 gating must mirror exactly:

- **Producer:** `.github/workflows/ci.yml` `m3-sync-e2e` job, L518–528:
  ```yaml
  - name: Write M3 E2E artifact
    run: |
      printf 'sha=%s\npassed_at=%s\n' "${GITHUB_SHA}" "$(date -u +%Y-%m-%dT%H:%M:%SZ)" > .m3-e2e-passed

  - name: Upload M3 E2E artifact
    uses: actions/upload-artifact@v4
    with:
      name: m3-e2e-passed-${{ github.sha }}
      path: .m3-e2e-passed
      include-hidden-files: true
      retention-days: 30
  ```
- **Consumer:** `.github/workflows/release.yml` L146–155 downloads `m3-e2e-passed-${RELEASE_SHA}` for the deploying SHA and aborts the release if the artifact is missing:
  ```yaml
  gh run download \
    --repo "${{ github.repository }}" \
    --name "m3-e2e-passed-${RELEASE_SHA}" \
    --dir .
  if [ ! -f .m3-e2e-passed ]; then
    echo "::error::.m3-e2e-passed artifact was not downloaded"
    exit 1
  fi
  ```
- **Format:** plain text `sha=<sha>\npassed_at=<ISO8601>\n`. The release workflow further parses it via `verify-production-runtime.mjs` to assert the artifact's `sha=` matches `${RELEASE_SHA}`.

**Implication for Phase 1 §4.5:** the V1 probe artifact MUST follow the same shape (`.vu1-probe-passed` with at minimum `sha=`, `passed_at=`, plus per-criterion status keys), uploaded with name `vu1-probe-passed-${{ github.sha }}`. Phase 6's level-flip PR consumes it identically: download → assert exists → assert `sha=` matches → assert all V1-C* keys are `pass`. Without this artifact for the current SHA, the level flip is rejected.

The brief's §0.5 ("Gating discipline") and §10 ("PR & commit discipline") demand this. Honor it verbatim.
